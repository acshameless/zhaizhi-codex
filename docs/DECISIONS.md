## 已确认

### D-001 站点公开

站点对所有人可见、无需登录。公开是产品定位的一部分：它是一座"可以被看见的私人图书馆"。

影响：所有页面走静态生成，无鉴权、无账号、无服务端。

### D-002 代码开源

代码以开源方式存放在 `acshameless/zhaizhi-codex`。内容是否与代码同仓，见待确认 Q2。

### D-003 录入方式：本地编辑 + 网页追加

电脑端用本地编辑器改 Markdown 后 push；手机端用浏览器在仓库网页上追加一条。MVP 不做自定义后台。

理由：两条路径都只需要 Git，不引入数据库与服务端，符合"十年可用"。

### D-004 不做存量导入

当前没有存量摘抄需要迁移。未来若出现（微信读书 / 备忘录 / Kindle / 纸质书拍照），用 AI 按数据模型批量转换后写入，不进 MVP 范围。

### D-005 MVP 功能范围

重点三屏：全局搜索、今日重逢、时间轴。书架页与书页作为数据结构的结构性出口保留为必须项（搜索结果必须回落到书，时间轴依赖书籍数据）。

### D-006 内容形态：一书一文件

一本书 = 一个 Markdown 文件（`books/<slug>.md`），书内摘抄以 `### q-001` 分块，原文用引用块，元数据用列表，个人想法用独立段落。

理由：一本书的全部内容在一屏内可读可改；单文件 diff 干净；Codex 与人类都能稳定追加。

### D-007 技术栈

Astro + TypeScript + Tailwind CSS v4 + Pagefind + Cloudflare Pages。零数据库、零服务端。

### D-008 弃用 Contentlayer

Contentlayer 在 npm 上的最后一次发布是 2023-06-29（`contentlayer@0.3.4`），已停止维护。改用 Astro 原生内容集合（Content Collections）做 Schema 校验与内容解析。

### D-009 搜索方案采用 Pagefind

不采用 FlexSearch：FlexSearch 的中文分词与排序质量不足，而"中文句子级检索"是本项目的核心承诺。Pagefind 官方支持中文（zh）专用分词，构建期生成索引，运行时零外部请求。

### D-010 设计系统直接采用 Kami 的设计令牌

暖纸底色 `#f5f4ed`、唯一强调色墨蓝 `#1B365D`、衬线排版。Kami 为 TW93 的开源项目（MIT），其定位是为 AI agent 提供文档与落地页的排版规则，因此可直接沿用其规则，而不是凭感觉模仿。

字体：英文 Charter，中文自托管 Noto Serif SC（OFL）。Kami 使用的仓耳今楷02 个人使用免费、商用需授权，未获授权时不打包进站点。

可选：`npx skills add tw93/kami -a codex` 可让 Codex 直接按其排版规则产出一致风格的文档与落地页。

### D-011 私密开关的语义

`私密: true` 的摘抄在构建期被完全剔除：不进入页面、搜索索引、时间轴与今日重逢。

重要边界：它只控制站点展示，不保护仓库源文件。若仓库公开，源文件仍可被任何人读到（见 Q2）。

### D-012 允许搜索引擎收录

不启用全站 noindex。站点公开且允许被搜索引擎收录，`私密` 内容从站点与 sitemap 中排除。

理由：作者已确认摘抄公开无风险，且公开的图书馆在被找到时才有公共价值。

复盘口径：若日后希望收敛曝光面，只需在站点配置中加一行 `X-Robots-Tag: noindex` 或 robots 规则，不需要改动内容与架构。

### D-013 双仓结构：公开代码 + 私有内容

两个仓库，各司其职：

| 仓库 | 可见性 | 内容 |
| --- | --- | --- |
| `acshameless/zhaizhi-codex` | 公开 | 站点代码、文档、CI 脚本、示例内容 |
| `acshameless/zhaizhi-content` | 私有 | 真实摘抄 `books/*.md`、封面等资源 |

构建路径：Cloudflare Pages 连接私有内容仓；构建时把公开代码仓（无需凭据）克隆进来，用内容仓作为内容源，产物部署到 Pages。这样私密条目在源码层面也不外泄，`私密` 开关才具备真实语义。

本地开发：代码仓通过 `ZHAIZHI_CONTENT_DIR` 指向本地内容仓目录；未设置时使用仓内 `examples/`（虚构示例内容），因此公开代码仓可独立构建、供他人复用。

本地仓库位置约定：代码 `/Users/shameless/Github/codex/zhaizhi`，内容 `/Users/shameless/Github/codex/zhaizhi-content`。

## 历史问题与解释（已解决）

### Q1 索引策略（已解决 → D-012）

解释："公开"与"被搜索引擎收录"是两件事。公开 = 拿到链接的人能看；noindex = 搜索引擎不把页面放进结果页。选择 noindex 的常见理由：

1. 摘抄含他人作品原文，被大规模收录会放大版权与抓取风险。
2. 个人图书馆不需要 SEO 流量，也不需要被陌生人围观。
3. 一旦被收录，删除后仍可能在缓存与第三方镜像中残留。

代价：朋友搜不到站点，只能靠链接访问；站点的公共价值会低一些。

结论：允许索引，`private` 内容从 sitemap 排除；保留一行配置即可切换为全站 noindex。

### Q2 仓库策略：内容放哪里（已解决 → D-013）

解释：代码开源与内容公开是两件独立的事。若代码与摘抄同处一个公开仓库，会带来三个后果：

1. 任何人都能一次性拿到你全部摘抄原文，包括私密条目的源文件。
2. 编辑历史永久可查：改过的措辞、临时草稿、删掉的内容都能从 Git 历史里翻出来。
3. 一旦被 fork，你无法收回；删除只对当前分支生效。

三种可选方案：

| 方案 | 含义 | 代价 |
| --- | --- | --- |
| 单仓公开 | 代码与内容同仓、全部公开 | 最简单；内容与历史完全公开，私密开关形同虚设 |
| 单仓私有 | 仓库私有，站点通过 Cloudflare Pages 公开部署 | 同样简单；代码暂时无法被别人复用 |
| 双仓 | 公开代码仓 + 私有内容仓，构建时跨仓拉取 | 真正的分区；需要多一步 CI 配置 |

结论：采用双仓。代码仓公开，内容仓私有，私密开关因此具备真实语义。

### Q3 书架页与书页

原始需求包含"回顾一本书里摘了哪些句子"，因此书架页与书页作为 MVP 必须项保留；搜索、今日重逢、时间轴是重点三屏。若日后希望收窄，可单独调整，不影响数据模型。
